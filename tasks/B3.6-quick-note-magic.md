# TASK B3.6: Quick-Note Magic — enrichment for how people actually write

PRECONDITION: B3.5 complete (hybrid retrieval, calibrated quality bar, deterministic provenance, claims-v2, eval harness). READ: `docs/intelligence-layer.md` (signal map + knobs), `tasks/B3.5-margin-retrieval-quality.md`, `scripts/eval-personas.ts`.

## Why this task exists (persona study, 2026-07-02)

B3.5's magic gate was calibrated on an idealized user: a deep student writing
paragraph notes dense with typed scripture citations. Real capture looks like
`"grace > performance. stop trying to earn it."` — short, colloquial,
reference-free. We simulated three realistic personas (13 notes) and measured,
through the SHIPPING pipeline, whether the note a deep Bible student would
expect to resurface for a passage actually surfaces (`npm run eval:personas`):

| Persona | Style | Expected resurfacings that surfaced |
|---|---|---:|
| Quick Capturer | 5–15 words, phone, no refs ("The shepherd knows my name.") | **0/6** |
| Sermon Sketcher | thematic ideas, illustrations, no refs ("The table is where outsiders become family.") | **0/4** |
| Devotional Journaler | first-person, emotional, no refs ("Forgave Dad today. Ten years of weight, gone.") | **0/3** |

**Every channel fails these notes, for structural reasons:**

1. **Reference evidence: dead.** No typed refs → zero anchors (0/13) → no
   crossref/chapter evidence — AND invisible to claim extraction, which
   gathers notes by anchor overlap only.
2. **Dense: bands don't transfer.** True-match sims for short notes measured
   0.53–0.60 (shepherd→PSA 23: 0.599; whispers→1KI 19: 0.596) — above
   short-note noise but below the 0.66 floor calibrated on paragraph notes.
   The idiom gap ("why does God feel silent??" vs Psalm 13's translation
   wording) can't be closed by floor tuning; the overlap is intrinsic.
3. **Lexical: blocked by design.** Several notes rank BM25 #1–#2 for their
   expected passage ("Baptism means belonging" is #1 for ACT 19) but the
   0.62 soft floor vetoes them — correctly, per B3.5's calibration, because
   at long-note calibration these dense scores are indistinguishable from noise.

Conclusion: **the missing ingredient is interpretation, not tuning.** Bridging
"the shepherd knows my name" → Psalm 23 requires understanding the note once —
a capture-time job for the LLM — after which retrieval stays deterministic,
explainable, and tunable. This is working backwards from magic: the expectation
is "I jotted a thought months ago; the app hands it back at the right passage,
and tells me why." Every gate below serves that sentence.

## Design: Note Enrichment (one background job powers everything)

On note create/edit (debounced, budget-enveloped per INV-16), a background
DeepSeek job produces an **enrichment record** — Derived data (INV-2:
regenerable; INV-1: never written into the note file):

```
enrichment (embeddings.sqlite or library.sqlite Derived table):
  note_id, content_hash, extractor (model@enrich-v1),
  inferred_refs:   [{ book, chapter, verse, confidence, why }]   (validated against backbone)
  themes:          2-4 ids from a CONTROLLED vocabulary (~120 biblical themes, data asset)
  expansion:       1-2 sentences restating the note in explicit biblical language
                   ("God's personal attentive care for each person, like a shepherd
                     who knows each sheep by name")
```

How each retrieval channel consumes it:

| Channel | Today | With enrichment |
|---|---|---|
| Reference | typed refs only | + inferred refs (lower weight, distinct provenance) → crossref/chapter evidence works for quick notes; chip: **"Possibly about Psalm 23 (AI-inferred — tap to confirm)"** |
| Dense | note chunks only | + one `noteId#exp` expansion chunk — the expansion closes the idiom gap (it speaks the passage's language), floors stay unified |
| Lexical | raw body | unchanged (expansion is NOT in FTS — keeps BM25 honest to the user's own words) |
| Claims | anchored notes only | inferred-ref notes become extraction-eligible (marked, lower default confidence) |
| Capture-time echo | none | on save: margin whispers "Sounds like Psalm 23 · John 10 — anchor it?" One tap promotes the inferred ref to a USER-authored anchor through the broker (like pin-claim; INV-1-compliant). Confirmed anchors = full-strength evidence forever after. |

### Model routing (decided 2026-07-02)

Route by (error catchability × call frequency), not one-model-everywhere:

- **Interactive margin**: no remote LLM ever — local embeddings + deterministic logic (existing decision).
- **Claims extraction**: budget tier (`deepseek-v4-flash`, thinking on) — the
  claims-v2 validator machine-catches weak-model failures (quote verification,
  backbone anchors), so weakness costs retries, not wrongness.
- **Enrichment**: STRONG tier by default — plausible-but-wrong inferred refs
  pass every schema check and only surface as user distrust; volume is capped
  by human typing speed, so cost is trivial (fractions of a cent per note).
- **One-time data builds** (passage glosses, theme vocab): strong model,
  developer-side, frozen as shipped data.

Config: two named tiers (`AI_MODEL_FAST` / `AI_MODEL_DEEP`) on the existing
OpenAI-compatible provider abstraction.
- FAST = `deepseek-v4-flash` (proven live for claims).
- DEEP = **GPT-5.5 via OpenAI API key** (HUMAN 2026-07-02; official docs at
  developers.openai.com; key to be provided). Live smoke before relying on it.
Escalation ladder: enrichment tries FAST first; validator rejection, low
confidence, or ambiguity flags escalate to DEEP. Gate E2's `smoke:enrich`
hand-check over the persona notes doubles as the FAST-vs-DEEP precision
measurement — tier defaults get set from that data.

**Codex-subscription route (researched 2026-07-02; HUMAN DECISION, revised):**
mechanically viable (Codex app-server is a JSON-RPC service any local client
can drive; Codex OAuth bills the user's subscription). Initial assessment
flagged ToS-gray risk; HUMAN overrode with context: OpenAI actively welcomes
personal/OSS tools driving Codex outside official harnesses (public statements
by OpenAI staff), unlike the earlier Anthropic posture (which Anthropic itself
has since softened). DECISION: **wire up `CodexAppServerProvider` now** as a
first-class DEEP-tier transport (user signs in with their own ChatGPT plan);
human will revisit if OpenAI signals otherwise. BYOK API key (GPT-5.5) remains
the parallel path once a key is configured. Dev machine has codex-cli 0.142.5
authenticated — live spike in Gate E2.

Trust rules (non-negotiable):
- **Stance preservation (anti-normalization)**: the expansion RESTATES the
  user's thought — it never evaluates, corrects, or drifts it toward the
  majority reading. Negations/contrasts are preserved explicitly ("affirms X
  as opposed to Y"), because embeddings hold "what it's about" but cannot
  reliably hold a "not" — stance lives symbolically (anchors/claims/threads),
  never only in vectors. Golden eval cases: minority-reading notes ("John 14
  is about the Spirit coming, not going to heaven"; "Galatians is about
  covenant belonging, not works-for-salvation") whose expansions must not
  contradict the note — hand-checked in `smoke:enrich`, and a reason to route
  enrichment to the DEEP tier (weak models normalize more).
- AI-inferred evidence is ALWAYS visually distinct from user-cited evidence.
- Confirmation is the only path from inferred → authored (INV-1).
- Enrichment failures degrade silently to today's behavior — never block capture.
- `enrich-v1` prompt version + content_hash → incremental, idempotent re-runs
  (same pattern as embeddings sync and claims extractors).

## The Quick-Note Magic Gate (acceptance)

Extend `eval:personas` from diagnostic to gate:

- **Q1**: ≥ 9/10 quick+sermon persona expectations resurface (from 0/10),
  each with an honest reason chip naming its evidence (inferred ref / theme /
  expansion). (Journal persona deprioritized by human decision — kept in the
  diagnostic report, out of the gate.)
- **Q2**: silence cases still hold — persona notes must NOT surface for LEV 13
  / EST 3 (enrichment must not spray false anchors); `eval:margin` M1–M4
  unchanged.
- **Q3**: capture-time echo suggests at least one correct passage for 10/13
  notes; a confirmed anchor upgrades the note to full reference evidence.
- **Q4**: every enrichment is inspectable in the UI (why did AI think this?)
  and re-derivable (delete Derived → rebuild reproduces it modulo model
  nondeterminism; store extractor version).

## Healing (ambiguity + evolving user intent)

A note like "the shepherd knows my name" is genuinely ambiguous (Psalm 23 vs
John 10). Later notes reveal the user's lean. Design rules:

1. **Preserve ambiguity**: enrichment stores MULTIPLE inferred refs with
   confidence; all surface as "possibly about". Never pick-one-and-hide.
2. **Behavioral healing (deterministic, no LLM)**: confirm/dismiss signals
   adjust confidence on related inferences (keyed by shared theme). Explainable:
   "suggested because you anchored a similar note to John 10".
3. **Contextual re-enrichment**: a new note triggers re-enrichment of its top
   semantic neighbors with the new note as context; keyed on
   (content_hash + neighbor_set_hash) — incremental, idempotent, budgeted.
4. **GUARDRAIL — heal interests, never model doctrine**: no hidden theological
   profile biasing retrieval (filter-bubble risk). The user's evolving view
   lives in visible, editable threads. Confirmed/authored data is never
   silently rewritten (INV-1/INV-4 spirit).

## Magic-breaker register (found 2026-07-02; each needs an owner gate)

**Live bugs (exist today, independent of enrichment):**
- **B-1 Stale claims**: claims are not invalidated when their source note is
  edited/deleted — a claim can display a now-false verified quote. Fix:
  content-hash invalidation per note, mirroring embeddings sync. (Feeds B3 Gate 3.)
- **B-2 Quick-capture refs unparsed**: the anchor extractor reads "Acts 19:2"
  but not `ps23` / `jn3` / `rom8` / `1cor13` — the dominant quick-capture ref
  style. Deterministic normalizer = full-strength reference evidence with zero
  AI. → promoted to **Gate E0** below.
- **B-3 Silent degradation**: embedding-model download failure yields a silent
  empty margin — indistinguishable from honest silence. Needs an AI-status
  surface in the margin.

**Trust erosion (must be designed into E2-E4):**
- **A-1 Zombie suggestions**: dismissals must key on (noteId, ref), not
  content_hash, or edits resurrect dismissed suggestions.
- **A-2 Anchor spray / proximity noise**: many-ref notes surface everywhere;
  "in this chapter" is meaningless in Psalm 119. Cap chapter-proximity by
  verse distance; dampen evidence from notes with many anchors.
- **A-3 Repetition decay**: same 5 notes for a popular chapter forever —
  rotation/seen-dampening once the feedback loop exists.
- **A-4 Privacy landmine**: journal-style notes ("Forgave Dad today")
  resurfacing during projected sermon prep. Private flag on notes, excluded
  from the margin by default; enrichment must classify personal notes as
  no-suggestion candidates.
- **A-5 Accidental confirms**: unanchor must be one tap, symmetrical with anchor.
- **A-6 Cold start**: with a tiny library the honest empty state must set
  expectations ("your margin grows as you take notes"), or silence reads as broken.
- **A-7 Admin notes that sound biblical**: names (Sarah, Aaron) and sermon-topic
  words in logistics notes must not earn inferred refs — enrichment needs an
  explicit "administrative / no scripture intent" output class (persona
  distractors are the regression corpus for this).
- **A-8 Translation mismatch**: "wording overlap" evidence is computed against
  WEB while the user may read KJV — either compute against the active
  translation or soften the chip label.

## Product decisions (HUMAN, 2026-07-02)

1. **Identity: AMPLIFIER, not commentator.** The AI organizes and resurfaces
   the user's material; it never authors interpretation shown in the UI.
   Passage glosses, if built, are internal-only (embedding fodder).
2. **Voice attribution (major new design element).** Notes carry a `voice`:
   `mine` (default) or an attributed source (podcast/sermon/class/blog/
   uploaded commentary — e.g. Tim Mackie, BEMA, Piper). Voices disagree and
   must never be blended into one "you":
   - one-tap attribution at capture; enrichment may SUGGEST attribution,
     never set it;
   - claims display their voice ("Piper — via your note");
   - healing/confirm signals learn ONLY from the user's own voice;
   - threads become disagreement maps: voices side by side, tension visible;
   - notes derived from ingested sources (M4 PDFs, future podcasts) inherit
     the source's voice automatically;
   - **self-authored external content** (the pastor's OWN blog/sermons/
     podcasts) is a third category: "me, published" — still the user's voice
     (healing may learn from it) but claims show the medium ("your sermon,
     Mar 2025"), and self-citation must be deduped so a sermon quoting the
     user's own note never counts as two independent witnesses (fake
     corroboration is a magic-breaker).
   ⚠ Requires a note-frontmatter field → Substrate format contract amendment
   (deliberate, versioned, with migration — do NOT slip it in).
3. **Journal capture: deprioritized.** Not a primary persona for now (possible
   later add-on). Drop journal notes from the Q1 gate denominator (gate is
   now over quick+sermon personas, 9/10). In exchange: two simple, visible
   per-note exclusion controls —
   - "hide from intelligence" (no embeddings / enrichment / claims / margin);
   - "hide from search" (also out of FTS).
   Clear aesthetic, one place, no buried settings.
4. **Margin loudness: pin = consent.** AI content appears only in the pinned
   state; ambient reading and chapter overview stay deterministic and quiet.
5. **Inferred refs: surface them, with restraint.** Clearly chipped, hard cap
   per card; a dedicated INTELLIGENCE DESIGN PASS (visual language for all
   provenance/evidence chips: user/cited/inferred/voice) is scheduled once
   the intelligence layer is fully planned — we are not becoming a
   generic-AI-chips app. **UI bar (HUMAN): no cheap UI anywhere in the
   capture-echo/confirm flow — polished, matching or exceeding the sharp
   minimalist modern look of the main reading page. E4 gets real design
   time, not just wiring.**
6. **Themes are user-owned.** The ~120-theme vocabulary ships as a seed; the
   individual edits/owns their list (it is a confessional document).
7. **No fake precision.** No confidence bands anywhere; inferred evidence is
   marked "AI-inferred", nothing more granular.
8. **Register discipline for all generated text** (expansions; any internal
   gloss): referent-dense, description-only; banned-register lexicon check
   ("reminds us", "beautiful picture of", application language) enforced in
   validation like claims-v2 rejects; NET-Bible-note register exemplars in
   the prompt; E2 hand-check scores referent density + stance fidelity +
   zero banned phrases.

## Staged plan

### Gate E0 — Deterministic quick-ref normalizer (no AI, biggest cheap win)
Extend ref parsing to quick-capture forms (`ps23`, `jn 3`, `rom8:28`,
`1cor13`, `Ps. 23.1`) with a conservative grammar (no bare numbers). Fixes B-2;
persona notes that DO contain slangy refs become fully-anchored user evidence.

Typo tolerance (HUMAN 2026-07-02: be thorough), layered and deterministic:
1. Canonical abbreviation table — every standard abbrev per book
   (`ps/psa/pslm`, `jn/jhn/joh`, `1co/1cor/icor`, `gn/gen`, ...), data-driven.
2. Curated common-misspellings list (`galations`, `phillipians`,
   `revelations`, `pslam`, `isiah`, `ecclesiates`, ...), editable word list.
3. Edit-distance-1 on full book names as last resort.
Safety rules: fuzzy layers (2-3) fire ONLY with adjacent chapter/verse digits
("pslam 23" ✓, "song 2 my kids" ✗); ambiguous stubs never match ("ju" →
Jude|Judges = no match); every layer is an editable data file (tunable, no AI).
Test corpus: seeded misspelling fixtures + persona notes; false-positive
regression is the gate (a wrong anchor is worse than a missed one).

### Gate E1 — Enrichment contract (pure core, like claims-v2)
`src/core/ai/note-enrichment.ts`: `enrich-v1` prompt (note text in, strict JSON
out), validation (refs against backbone; themes against the controlled
vocabulary; expansion length-capped; rejects-not-repairs), theme vocabulary
data asset (`data/themes.json`, ~120 entries: id, label, brief gloss). Unit
tests incl. injection resistance and hallucinated-book rejection.

### Gate E2 — Enrichment store + background job
Derived table + incremental sync keyed on (content_hash, extractor); JobQueue
wiring with budget envelope; live smoke (`smoke:enrich`) over the persona
corpus: measure inferred-ref precision by hand-checking the 13 notes.

### Gate E3 — Retrieval integration
Expansion chunk embedded (`noteId#exp`, document role); inferred refs feed
`computeReferenceHits` with `kind: "inferred"` and distinct label/chip; claims
eligibility widened. Re-run `eval:personas` → Q1/Q2 numbers pinned as the gate.

### Gate E4 — Capture-time echo + confirmation
Note editor saves → enrichment → margin suggestion card; confirm writes a real
anchor through the existing broker path (user action, INV-1); unanchor is one
tap (A-5); dismissals sticky per (noteId, ref) (A-1). Q3 live QA via CDP.

### Gate E5 — Healing
Behavioral confidence adjustment (confirm/dismiss propagation by shared theme)
+ neighbor re-enrichment on new-note arrival. Gate: the two-shepherd-notes
scenario — confirming John 10 on note B measurably re-ranks the suggestion on
note A, with the explanation chip naming why.

### Deferred / revisit
- Passage-side theme glosses (per-chapter, per-translation data asset) — helps
  ALL notes, but is a 1189-chapter data build; revisit if Q1 falls short of
  9/13 with note-side enrichment alone.
- Length-banded floors — likely unnecessary once expansions exist (they put
  quick notes back in the calibrated band); measure before adding a knob.
- Feedback loop (dismiss/snooze) — after E4's confirm flow proves the pattern.
